# 通知方式の判断

## 第1段階（現在の実装）

Daily Routine は、ブラウザ標準の Notifications API と Service Worker を使用します。

- 通知許可は設定画面の明示的なボタン操作後にだけ要求します。
- テスト通知は、通知許可後に即時送信できます。
- 朝・帰宅後の設定時刻は、日本時間でアプリが開いている間に確認します。
- 通知をタップすると、インストール済みPWAまたはブラウザのアプリ画面を開きます。
- 画面を閉じた状態やOSがブラウザ処理を止めた状態では、時刻通知を保証しません。

ブラウザだけのJavaScriptタイマーは、タブを閉じた後や端末の省電力制御下では動作し続けません。Service Workerにも任意時刻に自力で起動する標準APIはありません。

## 端末ごとの見込み

| 環境                              | 通知許可・テスト通知 | アプリを開いている間の時刻確認 | 完全に閉じた状態の確実な通知 |
| --------------------------------- | -------------------- | ------------------------------ | ---------------------------- |
| Android（対応ブラウザ/PWA）       | 対応                 | 対応可能                       | Web Push送信元が必要         |
| iPhone（ホーム画面に追加したPWA） | iOS 16.4以降で対応   | OS制御の範囲内                 | Web Push送信元が必要         |
| 通常のiPhoneブラウザタブ          | 制約が大きい         | 保証不可                       | 非対応                       |

端末やOSの設定、省電力、通知の集中モードによっても配信表示は変わります。

## 第2段階（確実な指定時刻通知）

個人利用・無料枠を優先する構成案は次のとおりです。

1. PWAでPush APIの購読情報を取得する。
2. 購読情報と通知時刻・タイムゾーンを、認証された利用者ごとに保存する。
3. GitHub Actions cron、Supabase Edge Functions + Cron、またはCloudflare Workers Cron Triggersで毎分〜数分ごとに対象を判定する。
4. サーバー側からVAPID鍵を使用してWeb Pushを送る。
5. Service WorkerがPushイベントを受け取り通知を表示する。

候補の中では、少人数の個人利用なら Cloudflare Workers + D1 + Cron Triggers、または Supabase + Edge Functions が小さく始めやすい構成です。Firebase Cloud MessagingはAndroidとの相性が良い一方、Web Push購読とプロジェクト設定が増えます。

実装時は次を守ります。

- VAPID秘密鍵、サービスロールキー、Firebase秘密情報をリポジトリへコミットしない。
- フロントエンドに置ける公開キーと、サーバー専用秘密情報を分離する。
- `.env.example`には変数名だけを記載する。
- 購読解除、期限切れ購読の削除、送信失敗の再試行上限を用意する。
- 時刻は利用者のタイムゾーンと夏時間を含めて判定する。

現バージョンは外部サーバーへ個人データを送信しない方針を優先し、第2段階は設計のみです。
